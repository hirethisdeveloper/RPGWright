# `runner/` and `bin/rpgwright.js`

## Why a bundled runner exists, and its actual scope

Per §2/§10 of the plan, `rpgwright test` is the primary, documented interface — with the low-level `launchGame()` core staying available as an unsupported escape hatch for embedding in another test runner. The scope of what this runner needs to do is narrower than a general-purpose test framework: it exists specifically to remove the launch/run/stop boilerplate around `GameDriver`, for tests that are fundamentally "launch an app, drive it, assert." It is **not** a replacement for `node:test` as a general unit-test runner — see [[testing-strategy]] for why RPGWright's own internal unit tests (of `pty.js`/`terminal.js`/`assertions.js`/`keys.js`) deliberately stay on `node:test` rather than being forced through this runner's app-launching fixture model.

## Config resolution (`runner/config.js`)

`loadConfig({ configPath, cwd })` finds `rpgwright.config.js` (explicit `--config` path, or `<cwd>/rpgwright.config.js`), `require()`s it, and validates that it exports a `command` — the one field with no sensible default, since RPGWright has no built-in notion of what app to launch. Everything else launch-related (`cols`, `killSignal`, `getDiagnostics`, `keys`, `snapshotsDir`, ...) is passed through **untouched**, not re-defaulted here — `src/game.js`'s `launchGame()` already owns those defaults, and duplicating them in the config loader would create a second source of truth for the same values. Only genuinely runner-level concerns get defaults at this layer: `testDir` (the config file's own directory, unless overridden), `testMatch` (`['**/*.rpg.test.js', '**/*.rpg.test.ts']`), and `timeout` (30000ms — the *test-level* timeout, distinct from `expectTimeout`, which bounds individual assertions).

## Discovery (`runner/discover.js`)

A hand-rolled glob-to-RegExp converter and recursive directory walker — not a `glob`/`minimatch` dependency. RPGWright's only two dependencies are `node-pty` and `@xterm/headless` (§4); `testMatch`'s real-world need is a handful of simple patterns (the default `**/*.rpg.test.js`/`**/*.rpg.test.ts` plus straightforward variants), which a ~20-line converter handles correctly without pulling in a third dependency for it. `node_modules`, `.git`, and `__snapshots__` are always skipped during the walk.

## Registration: scopes (`runner/test.js`)

Registration and execution are separate phases. `run.js` calls `_beginFile(file)`, `require()`s the file (which synchronously calls `test()`/`describe()`/`test.use()`/hooks), then `_collect()` returns that file's tests. **Every file is collected before any test runs**, so `test.only` in one file can narrow the whole run and filters can apply across files.

The registry is a tree of **scopes**: the file is the root scope and each `describe()` adds a child. A scope holds its `use` options, its four hook lists, a `mode` (`'skip'`/`'only'` from `describe.skip`/`describe.only`), and an optional `timeout`/`slow`. Each collected test keeps a reference to its declaring scope plus its `titlePath`, `file`, flags (`skip`/`only`/`fail`) and declaration `line`. The line is read off the stack in `callerLine()`, from the first frame inside the file being collected, and powers `file:line` filtering. `_scopeChain(scope)` returns root→leaf, which is how `run.js` resolves everything:

- **Options**: `Object.assign({}, ...chain.map(s => s.use))`, then spread over the config, so inner scopes override outer ones key by key.
- **Skip/only**: a test is skipped if it or any enclosing scope is skipped; if any selected test is `only` (itself or via a scope), the run is narrowed to those.
- **Timeout**: the innermost scope `timeout` wins over `config.timeout`; any `slow` in the chain triples it.

`test.eachViewport([viewports,] name, fn)` is pure registration sugar: it registers one ordinary test per viewport, named `name [<viewport name>]`, carrying a test-level `use: { cols, rows }` (merged after every scope's `use`, so the viewport wins) and its `viewport`. The config's `viewports` reach `test.js` through `_setConfig(config)`, which `run.js` calls before collecting any file, since registration happens at `require()` time. `loadConfig` validates and names them (`normalizeViewports`); viewports were made a registration-time expansion rather than a "projects"-style re-run of the whole suite, so only tests that opt in pay for the extra launches. The `viewport` fixture is the test's own viewport, or `{ name, cols, rows }` from the launched game's actual size.

`test.setTimeout`/`test.slow`/`test.step`/`test.info` are dual-purpose: at collection time (no running test) the first two configure the current scope; while a test runs, `run.js` runs it inside `_runWith({ games, info }, fn)` (AsyncLocalStorage, see below) and they act on the running test. `test.step` and `test.info` require a running test and throw a clear error otherwise.

## The `game` fixture's lifecycle (`runner/run.js`)

This is the runner's actual reason to exist. For each selected test (unless skipped), `runFile()`:

1. **Opens scopes** the test needs that aren't open yet, running each scope's `beforeAll` hooks (with `{}`, since there's no per-scope `game`), and **closes** scopes the previous test was in but this one isn't, running their `afterAll` hooks in reverse. So `beforeAll` runs right before a scope's first runnable test and `afterAll` right after its last. A `beforeAll` that throws is stored on the scope, and every test in that scope fails with that error without launching anything. An `afterAll` that throws is reported as a failed entry named `<scope> > afterAll`. Both run under their own deadline (`runScopeHooks`), the timeout a test in that scope would get: a hook awaiting a promise that never settles used to hang the run, or, with nothing left on the event loop, let it exit 0 with no summary. `runCli` also sets `process.exitCode = 1` up front and only lowers it at the summary, so any path that never reaches the summary can't pass.
2. Sets up the fixtures the test asks for (see below); `game` is `launchGame({ ...config, ...useOptions, scenarioName })`, fresh — a new `GameDriver`, new process, every test. No shared/reused fixture across tests, which is what makes tests independent of run order and immune to one test's leftover state leaking into the next.
3. Runs the `beforeEach` hooks root→leaf and the test, racing them (fixture setup included) against a **deadline** (`createDeadline`): a timer measured from the test's start, which `test.setTimeout(ms)`/`test.slow()` re-arm mid-test; `0` disables it. A body that loses the race is abandoned (JS can't cancel it), not awaited.
4. Runs the `afterEach` hooks leaf→root with the fixtures they asked for, once fixture setup finished. They run *outside* the abandoned body, so after a timeout they still run before teardown and before the next test starts (they used to run whenever the abandoned body got to them, overlapping the next test); after a timeout they get a fresh deadline of the same length. The body's error wins over a later `afterEach` error.
5. Tears the fixtures down (stopping `game` and anything from `launch()`) — always, whether the test passed, failed, or timed out. `teardown()` closes the scope first: an abandoned body (or a slow fixture) that sets something up afterwards has it undone on the spot and gets an error, instead of registering a teardown nobody will run — that used to leave the app running and the CLI hanging after the summary. `stop()`'s own idempotency (see [[game-driver]]) means a test that already called `game.stop()` itself for its own reasons doesn't cause a problem when the runner's automatic call runs afterward.

A `test.fail` test inverts the outcome: it passes if it threw and fails with "Expected this test to fail" if it didn't. A `beforeAll` failure is never inverted.

## Selection and CLI options

Integer flags (`--retries`, `--workers`) check against the same limits as their config fields (`MIN` in `config.js`), and viewports are validated and named by `config.js`'s `normalizeViewports`/`viewportName` wherever they come from (config, `test.eachViewport`, the `viewport` fixture). `parseArgs` maps `--config`/`--grep`/`--grep-invert`/`--reporter`/`--max-failures`/`--trace`/`--retries`/`--repeat-each`/`--workers` (value flags), `--list`/`--update-snapshots`/`--fail-on-flaky`/`--watch`/`--ui`/`--save-run` (booleans) and positional filters; an unknown `--option` throws rather than being ignored, and so does `--ui` with `--watch` (see UI mode below). `selectTests` applies, in order: filters (`path` substring against the absolute path or the cwd-relative path; `path:line` must equal the test's own line or any enclosing describe's line), `--grep`/`--grep-invert` against the full ` > `-joined name, then `only`. `--list` prints `file:line › name` for the selection and returns without launching anything. `--reporter` overrides `config.reporter`. `--update-snapshots` passes `updateSnapshots: true` to `launchGame` (whose own default still reads `RPGWRIGHT_UPDATE_SNAPSHOTS=1`, so the env var keeps working). `--max-failures` stops launching tests once that many have failed, still closing open scopes, and prints why it stopped.

## Fixtures (`runner/fixtures.js`)

Fixtures are lazy. `requestedFixtures(fn)` reads the names a test, hook or fixture destructures from its first parameter by parsing `fn.toString()` (with `splitTopLevel` so defaults like `{ a = { x, y } }` don't confuse it). It returns `null` when it can't tell (a non-destructured or rest parameter). For a test or hook, `resolveAll(null)` then provides every fixture *except* `tmpHome`: whether the game gets an isolated `HOME` must not hinge on how a parameter is spelled (it used to, which silently redirected `HOME` for `async (fx) => …` tests). For a fixture definition, `null` means no dependencies. Comments inside the pattern are stripped before reading names. `run.js` unions the names from `beforeEach` hooks, the body and `afterEach` hooks, and `createFixtureScope` creates exactly those, each once per test, dependencies first, recording a teardown for each; `teardown()` runs them in reverse and reports the first error (which fails a test that otherwise passed).

This changed one long-standing behavior: **`game` is now launched only for tests that ask for it.** Tests that don't touch the app (setup checks, pure-logic tests sharing a file) no longer spawn a process. A test whose parameter can't be read (not destructured) still gets a `game`, as before.

Built-ins: `game` (via `launch(launchOptions)`), `viewport` (the eachViewport size, else the game's size), `launch` (a factory for extra processes, each stopped at teardown), `tmpHome` (a temp dir, seeded from the `homeFiles` option and removed at teardown), and `testInfo`. Whenever `tmpHome` is requested or `homeFiles` is set, every launch gets `HOME=tmpHome`; the scope records the full requested set *before* creating anything, because fixtures resolve concurrently and `game` could otherwise start before `tmpHome` was pending. `createFixtureScope` also takes an optional `onGame(game, testInfo)`, called for every process `launch()` starts (the `game` fixture included) right after it's pushed onto `games`; `runTest` passes `cliOptions.onGame`, which only the UI reporter sets. User fixtures come from `test.extend(defs)`: `test.js`'s `createTestApi(fixtureDefs)` builds a complete `test` (variants included) whose registrations carry the merged `fixtureDefs`; non-registering methods (`use`, hooks, `describe`, `step`, ...) are shared. A definition is a value, or `async (deps, use, testInfo)`, run until it calls `use(value)` and resumed at teardown. Redefining a built-in throws.

`beforeAll`/`afterAll` still receive `{}`: their fixtures would have to outlive a single test, which this test-scoped model doesn't provide. Pure internal unit tests still belong on `node:test` (see [[testing-strategy]]).

## Retries, flaky tests, repeat-each

`retries` (config, validated non-negative, default 0) or `--retries` reruns a failed test with fresh fixtures, up to that many times; `testInfo.retry` says which attempt is running. A `beforeAll` failure is never retried. A pass after a retry goes to `reporter.testPassed(name, ms, { retry })`, which counts it as passed *and* flaky; `--fail-on-flaky` turns any flaky test into exit code 1. With `trace: retain-on-failure`, each failed attempt gets its own trace (`(retry n)` in the name). `--repeat-each n` clones each selected test n times at plan time, named `[repeat i/n]`, with `testInfo.repeatEachIndex`.

## Traces (`runner/trace.js`)

`trace` (config, default `'off'`, validated by `validateTrace`) or `--trace` decides whether to write a trace per test: `'on'` always, `'retain-on-failure'` when the test's *final* outcome failed (after `test.fail` inversion, which is why the decision is made in `runFile` rather than `runTest`). The scope keeps every driver it launched (`game` and each `launch()`), in order, as `games`; `runTest` hands that list back through a `holder` object so `runFile` can call `getTrace()` on each after `stop()`, writing one trace per process (the second and later named `(process n)`). The same list is the run context's `games`, which `test.step` records a step on, so a test using only `launch()` still gets traces and step grouping. `buildTraceHtml` is a pure function of `getTrace()` plus the outcome: a self-contained page (inline CSS, `<details>` for expanding, no scripts) with the escaped failure report, every action with its screen (the failed ones open, step children indented), and the final screen. Files go to `outputDir` (config, default `test-results` next to the config file) as `<file-slug>--<test-slug>.trace.html`, the file slug taken from the path under `testDir` (extension stripped), with a per-run `traceNames` set numbering any collision (`-2`, …) — slugs are lossy and capped at 80 characters, which used to let a retry's trace overwrite the first attempt's, and a failing test's error message gets a `Trace: <path>` line appended. No trace is written for a test whose `beforeAll` failed, since nothing was launched. Every per-test file is named by `artifactPath` (the trace's `.trace.html`, the run file's `.run.json`); `tracePath` is just that with the trace extension.

## Run files (`runner/runfile.js`)

`saveRun` (config, boolean, default `false`, validated by `config.js`) or `--save-run` writes a `.run.json` per test: everything `rpgwright play` needs to replay the test's terminal sessions later without launching the app or running test code. Like a trace, it forces `record: true` on every launch (`runTest`), and `runFile` writes it after teardown from each launched driver's `getTrace()`. It is written for every test that launched at least one game and reached its *final* attempt — passed, failed (after `test.fail` inversion) or aborted from a UI session — and for nothing else: a skipped test, a failed `beforeAll`, or a test that never launched gets no file. With retries only the final attempt is written (earlier attempts' processes are gone from the file; their traces, if any, remain). Names come from `artifactPath` with the test's name (no `(retry n)` suffix) and a per-run `runNames` set separate from `traceNames`, so a test's run file sits next to its first trace under the same base name; rerunning a test in one `--ui` session numbers the later files (`-2`, …) rather than overwriting. A failing (not aborted) test's message gains a `Run: <path>` line with the `Trace:`/`Recording:` lines; the run file is written first, so its own copy of the report has none of them. It works with `--trace` (both are written), with `--ui` (the session goes through `runFile`), and is forwarded by `--watch` like any boolean flag.

Format, version 1 (`RUN_FILE_VERSION`), one JSON object:

```
{ "format": "rpgwright-run", "version": 1, "rpgwright": "<package version>", "recordedAt": "<ISO timestamp>",
  "test": { "title": "<full name incl. describe path>", "file": "<path under testDir>", "line": <n> },
  "result": { "status": "passed"|"failed"|"aborted", "durationMs": <n>,
              "error": null | { "message": "<first line>", "report": "<whole error message, ANSI stripped>" } },
  "sessions": [ { "command", "args", "cols", "rows",
                  "events": [[<sec>, "o"|"i"|"r", "<data>"]],
                  "actions": [{ "type", "detail", "ok", "depth", "t": <sec> }] } ] }
```

`sessions` is one per launched driver in launch order. `events` is `recording.events` verbatim (seconds since launch; `'r'` data is `"<cols>x<rows>"`, as `game.resize` records it); `cols`/`rows` are the size at launch. Action `t` is recorded in milliseconds since the same launch instant (`startedAt`), so `buildRunFile` divides it by 1000: events and actions then share one clock. Recorded actions' screen grids are left out (playback rebuilds screens from the events). For a GameDriver failure `error.message` *is* the §9 report, so `report` is the full block and `message` its first line. If a `launch()` call turned `record` back off, that session has no events and takes its size from the final screen.

`buildRunFile(details)` is pure (`recordedAt` is passed in; `writeRunFile` supplies the current time and returns the path). `readRunFile(path)` parses and validates, throwing an Error naming the file for: unreadable, invalid JSON, wrong `format`, a `version` other than the supported one (the message names the supported version), or a missing/malformed field playback depends on (`REQUIRED_FIELDS`/`SESSION_FIELDS`). Size: `recording.events` is unbounded — every output chunk and input write of the session is kept — so a long or output-heavy test makes a large file (and holds it in memory until the test ends); only enable it when you mean to replay.

## Parallel workers

`workers` (config, default 1) or `--workers` runs up to that many *files* concurrently, in one process (`runPlan`). That's enough because each test's real work happens in its own app process; the runner only interleaves waiting. Tests within a file stay sequential, since a file's `beforeAll`/`afterAll` scopes assume that. Two things made concurrency safe:

- **The running test is in `AsyncLocalStorage`**, not a module global. `run.js` runs each test body inside `test.js`'s `_runWith(run, fn)`, so `test.step()`/`test.info()`/`test.setTimeout()` always find *their own* test through the async context, even while another file's test is mid-await. (`_setCurrentRun` remains as a fallback for unit tests that call these outside a run.) `runner-e2e.test.js` has two parallel files whose steps fail at the same time to guard this.
- **Output stays deterministic.** With more than one worker, each file reports into a `bufferedReporter()`; when a file finishes, every completed file from the front of the plan is flushed to the real reporter in plan order. A parallel run prints exactly what a serial one would, just sooner; `runner-e2e.test.js` compares the two outputs directly.

`testInfo.workerIndex` lets tests partition shared external resources. `--max-failures` uses one shared budget; workers stop taking new files once it's spent.

## Services and global setup (`runner/services.js`)

`startRunEnvironment(config)` runs before the first test (only if there are tests to run, and never for `--list`): each `services` entry is started with `spawnPipe` and waited on (`readyText` in its output, `readyPort` accepting TCP connections, or immediately), failing with the tail of its output if it exits or times out; then `globalSetup` runs. It returns a teardown that unwinds in reverse: `globalSetup`'s returned function, `globalTeardown`, then each service (`game.js`'s `stopProcess`: SIGTERM, SIGKILL after 3s). The reverse-order unwinding is `unwind()` from `fixtures.js`, the same helper test fixtures tear down with. A failure part-way unwinds whatever had already started before rethrowing. `loadConfig` resolves the hook paths and each service's `cwd` against the config file's directory.

## Watch mode

`--watch` runs once, then `fs.watch`es (recursively) the test directory, the config's directory and any `watchPaths`, ignoring `node_modules`, `.git` and what a run writes itself (the resolved `outputDir` and `snapshotsDir`; hardcoding `test-results`/`__snapshots__` made a custom one retrigger forever). Changes are debounced (200ms) and a rerun never overlaps another. If every changed file is a discovered test file, only those files rerun; otherwise the original selection reruns. Every run, the first included, is a separate `rpgwright test` child process (same flags minus `--watch`, `stdio: 'inherit'`): evicting modules from `require.cache` used to work for CommonJS, but an ES-module test file (the documented `.ts` style, loaded via `require(esm)`) isn't re-evaluated that way and registered no tests on reruns. A fresh process also gives each run clean module state. It never exits on its own.

## TypeScript

`.ts` test files are matched by default (`**/*.rpg.test.ts`) and `require()`d like any other. On Node 22.18+ `process.features.typescript` is set and Node strips the types itself (and loads files using `import` syntax as ESM through `require(esm)`). On older Node, `ensureTypeScript` registers `tsx/cjs` if the *project* has `tsx` installed, and otherwise fails with a clear message, so RPGWright itself takes no dependency. The declarations live in `types/` (`index.d.ts` for the core, `test.d.ts` for the runner API and `Config`), wired through `"types"` conditions in `package.json`'s `exports`. Nothing compiles them against the JavaScript, so `test/types.test.js` checks for drift: every runtime export, `GameDriver` member (including `press.raw` and `mouse.*`), `LaunchOptions` field (against what `launchGame` destructures), built-in fixture, layout check, `test` method, locator method and matcher must be declared, and nothing declared may be missing at runtime. It checks names, not parameter or return types.

`engines` is `>=20`: `--watch` relies on recursive `fs.watch`, which Linux only has from Node 20 (Node 18 is also past end of life).

## Reporter (`runner/reporter.js`)

Five built-in reporters, selected by config's `reporter` field (a name, or a list of names and `[name, options]` pairs, combined by a forwarding composite whose totals come from the first) or `--reporter`. Every reporter receives the same events, which carry `{ retry }` and `{ file, line }` metadata. `json` and `junit` collect results (`createCollector`) and write `outputFile` (default `results.json`/`results.xml` in `outputDir`) at summary time; JUnit output strips the control characters XML 1.0 forbids (ANSI escapes in failure messages). `github` prints `::error`/`::warning` workflow commands, escaped per GitHub's rules, located at the test's file (relative to cwd) and line. The two console styles (`'list'`, the default, and `'dot'`) share one `printSummary()` — the failure-block dump and final summary line are identical between them; only the per-test progress indicator differs (`'list'`: a running ✓/✖ line per test; `'dot'`: a single `.`/`±`/`F`/`-` character for pass/flaky/fail/skip, Mocha-style). `createReporter(style)` looks the factory up in a small `REPORTERS` map and throws immediately (before any test runs) on an unrecognized name, rather than silently falling back to the default — a typo'd `reporter: 'dots'` in config should fail loudly, not quietly run with the wrong output shape. Respects `NO_COLOR` and non-TTY output (no ANSI codes when `process.stdout.isTTY` is false) for both styles.

Besides the per-result events there is one optional event, `testStarted(name, meta, attempt)`, sent by `runFile` at the start of every attempt (so once per retry), before `runTest` and also before a `beforeAll` failure is reported. Reporters that don't care simply don't define it: `combineReporters` (the composite, also used by `--ui`) and `bufferedReporter`'s replay both skip a method a reporter lacks. `printSummary(state, durationMs, log)` takes the line writer as a parameter so the UI reporter prints the same summary to its own (injectable) stdout.

## UI mode (`runner/ui.js`)

`--ui` swaps the console output for `createUiReporter`, a reporter that owns the terminal. `runTests` decides the output through `resolveOutput` (pure, unit-tested): with `--ui`, `workers` is forced to 1 (one live screen at a time) and the reporter spec is filtered to `FILE_REPORTERS` (`json`/`junit`), which are combined after the UI reporter so the totals still come from the UI's own `state`. It throws before running anything if `stdout.isTTY` is false (`stdout` is a `runTests` option so this is testable). `--watch` is rejected because every watch run is a child process with inherited stdio; a UI that re-entered the alternate screen per child is a different design.

Live data flows without polling: `runTests` passes `uiReporter.onGame` as `cliOptions.onGame`; the fixture scope calls it on launch; the UI subscribes with `game.observe()` (see [[game-driver]]) for the first game of the current test, marks itself dirty on `screen`/`action`/`exit` events, and disposes the subscription when the test's result arrives (the final frame stays up until the next `testStarted`, read from `getScreenCells()`, which returns the final grid after `stop()`). Steps are tracked as a stack of `step` action records: a record arriving with `ok === null` is pushed, the same record arriving again finished is removed. The only timer besides the frame throttle is an unref'd 1s tick that keeps the elapsed time moving.

Drawing: redraws are coalesced to at most one per 16ms (`schedule()` sets a single timer); each frame is one `stdout.write` wrapped in synchronized-output markers (`?2026`), every row absolutely positioned (`CSI row;1H`) and erased to its end, then `CSI J` below, so stray output can't accumulate. The app screen comes from `renderScreenAnsi` over a grid clipped to the space left after the header (2 rows), box border and footer (2 rows); `clipGrid` turns a wide character cut by the right edge into a space so every row stays exactly the clipped width. The box is centered horizontally and re-laid out on stdout's `'resize'` event. Header/footer text goes through `fit()`, which strips escapes and control characters before truncating.

**Terminal-restore contract.** `start()` (called by `interactive()`, which `runTests` calls after services are up, only if there are tests) writes `ENTER` (alt screen, hide cursor, autowrap off, clear) and installs guards; `close()` writes `LEAVE`, removes every guard and listener, restores `console`, and is idempotent. It runs from: `summary()`; `runTests`'s `finally` (so a thrown error is printed on the normal screen, as is the `--max-failures` notice); process `'exit'` (the CLI's own SIGINT/SIGTERM handlers exit, which lands here); `'uncaughtExceptionMonitor'` (before Node prints the crash); and its own SIGINT/SIGTERM handlers, which re-raise the signal if no other listener remains, so embedding `runTests` without the CLI still dies from Ctrl+C. While the alternate screen is up, `console.log`/`info`/`warn`/`error`/`debug` are held (formatted at call time) and replayed after `LEAVE`, so test output and the runner's own messages (unhandled rejections) aren't lost with the alternate screen. `stdout`, `proc` and `console` are injectable; `test/runner-ui.test.js` drives everything against fakes, and `runner-e2e.test.js` runs `--ui` for real under node-pty.

## UI session mode (`runner/session.js`)

With `--ui`, `runTests` doesn't run the plan: it wraps it in a session (`createRunSession` → `createSession`) and awaits `uiReporter.interactive(session, { autoRun })`, with `autoRun` true only when exactly one test is selected. The session's `tests` are the plan's tests after every selection step (filters, grep, only, repeat-each), one entry each — `{ id, title, file, line, status, durationMs, error, flaky }`, mutated in place. When `interactive()` resolves (the user quit), the `finally` closes the UI and services/globalTeardown as in a normal run, and `activeReporter.summary()` goes to the ui reporter first, which in session mode prints from `session.results()` (each run test's latest result; aborted counts as failed; afterAll failures from the latest `run()` add to `failed`). File reporters still receive every attempt of every run.

**Running on demand.** `session.run(ids)` groups consecutive ids from the same file and hands each group to `runFile` — the same function a normal run uses, so beforeAll/afterAll open and close around each group exactly as they would around a plan, fixtures are fresh per test, retries apply, and the reporter sees the usual events. A wrapping reporter keeps entry statuses current: `testStarted` marks the head of the group's queue `running`; each result (`testPassed`/`testFailed` with `meta`/`testSkipped`) settles and shifts it (runFile reports a group's tests in order, one result each); a `testFailed` without `meta` is an afterAll failure. Scope state (`open`, `beforeAllError`) is per `runFile` call, so the same test can run any number of times. `run()` rejects only on misuse (unknown id, a run already in progress); a failing test resolves normally.

**Run control.** The session passes a `control` object into `runFile` as `cliOptions.control` (absent outside a session, so a normal run pays nothing):
- `control.gate` becomes the `gate` launch option (see [[game-driver]]): every game action awaits it. Unpaused it returns `undefined`; paused it returns a pending promise (a "waiter"); `stepOnce()` releases one waiter (or, if none is waiting yet, lets the next action through) and stays paused; `resume()` releases all.
- `control.track(deadline)`: every `createDeadline` given a control registers `{ hold, release }`. While any waiter is held, every tracked deadline is held: its timer is cleared and, on release, the held time is added to its start, so a paused test doesn't time out. `deadline.clear()` untracks.
- `control.aborted` / `control.aborting`: `abort()` creates an `AbortError`, rejects `aborting` (raced by `withinDeadline` against the test body and against beforeAll hooks — never afterEach/afterAll, which must get to clean up), rejects any held waiters with it, and unpauses. `runTest` treats it like a timeout (afterEach gets a fresh deadline, teardown stops the games); `runFile` reports it via `testFailed` (status `aborted` in the session, because the error is `control.aborted`), skips `test.fail` inversion, retries and traces for it (its run file is still written, status `aborted`), and stops at the next test; the session stops at the next file group. Waiters still held when `run()` ends (an abandoned, timed-out body) are rejected rather than left for a later resume.

`test/runner-session.test.js` drives sessions in-process over real throwaway projects (the term-probe fixture): reruns, statuses, results, hooks, retries, abort (cleanup, cancellation), and pause/stepOnce/resume including a pause longer than the test's timeout.

## `rpgwright init` (`runner/init.js`)

Scaffolds a **genuinely self-contained, immediately-runnable** example — deliberately not a placeholder the consumer has to edit before anything works. The scaffolded target (`example-app.js`) is a dependency-free raw-mode Node script (just `process.stdin.setRawMode`/`process.stdout.write`), not an Ink app — so `rpgwright init && rpgwright test` passes with zero new dependencies and zero edits, immediately proving the tool works before a consumer wires it up to their real app. `writeIfAbsent` never overwrites an existing file unless `--force` is passed, so re-running `init` in a project that's already been customized is safe. If `package.json` exists, `"test:e2e": "rpgwright test"` is merged into its `scripts`; if it doesn't, that step is skipped with a clear message rather than fabricating a `package.json` (creating one from scratch isn't `rpgwright init`'s job).

## Self-referencing: how `.rpg.test.js` files can `require('rpgwright/test')` from inside this repo

Node resolves a package requiring its own name (as declared in its own `package.json`) via the `"exports"` map, without needing a `node_modules` entry — this is a stable, built-in Node feature (self-referencing), not an RPGWright mechanism. It's why the dogfood suites under `test/rpg/**` (see [[testing-strategy]]) can `require('rpgwright/test')` directly. It only resolves for files that are actually inside the package's own directory tree, though — testing `rpgwright init`'s scaffold from a truly external temp directory (as `test/runner-e2e.test.js` does) needs a real `node_modules/rpgwright` entry, which those tests create as a symlink to the repo root (the standard local-package-testing technique, equivalent to `npm link`).
